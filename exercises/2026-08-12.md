# 第 6 週今日練習題：使用者資料驗證與標準化錯誤回應

## 題目說明

建立一個「使用者管理」REST API，重點在於**請求資料的驗證**與**統一的錯誤回應格式**。在真實專案中，嚴謹的驗證與一致的錯誤訊息能大幅減少前端與後端的溝通成本，也能防止髒資料進入資料庫。

---

## 技術要求

- **Express.js**：路由設計、Middleware 驗證層、統一錯誤處理 Middleware
- **PostgreSQL**：`users` 資料表操作（INSERT / SELECT）、唯一鍵（unique constraint）衝突處理

---

## 具體任務

### 1. 建立資料庫資料表

```sql
CREATE TABLE users (
  id        SERIAL PRIMARY KEY,
  username  VARCHAR(30)  NOT NULL UNIQUE,
  email     VARCHAR(100) NOT NULL UNIQUE,
  age       INTEGER,
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```

### 2. 建立驗證 Middleware

在 `middlewares/validateUser.js` 中撰寫驗證邏輯（**不得使用第三方驗證套件**，純手工驗證）：

| 欄位 | 規則 |
|------|------|
| `username` | 必填；長度 3–30 字元；只允許英數字與底線 |
| `email` | 必填；需符合基本 Email 格式（`xxx@xxx.xxx`）|
| `age` | 選填；若提供，必須為整數且介於 1–120 |

驗證失敗時，middleware 應收集**所有**錯誤（而非只回傳第一個），並呼叫 `next(err)` 傳遞給錯誤處理 middleware。

### 3. 建立統一錯誤回應格式

在 `middlewares/errorHandler.js` 中定義全域錯誤 Middleware，所有錯誤一律以下列 JSON 格式回應：

```json
{
  "success": false,
  "status": 400,
  "message": "Validation failed",
  "errors": [
    { "field": "username", "message": "Username must be 3–30 characters" },
    { "field": "email",    "message": "Invalid email format" }
  ]
}
```

- 驗證錯誤 → HTTP 400
- 資料庫唯一鍵衝突（`username` 或 `email` 重複）→ HTTP 409，`message` 為 "Username or email already exists"
- 其他未知錯誤 → HTTP 500，`message` 為 "Internal server error"（**不可**將 stack trace 暴露給客戶端）

### 4. 實作 API 端點

| Method | Path | 說明 |
|--------|------|------|
| `POST` | `/api/users` | 新增使用者（需通過驗證 middleware）|
| `GET`  | `/api/users` | 查詢所有使用者（回傳陣列） |
| `GET`  | `/api/users/:id` | 查詢單一使用者；找不到時回傳 404 |

成功新增時，回傳 HTTP 201 與以下格式：

```json
{
  "success": true,
  "data": {
    "id": 1,
    "username": "alice",
    "email": "alice@example.com",
    "age": 28,
    "created_at": "2026-08-12T10:00:00.000Z"
  }
}
```

### 5. 手動測試情境

使用 `curl` 或 Postman 測試以下情境，並確認回應格式符合規範：

1. 正常新增一筆使用者 → 201
2. 重複寄送相同 `username` → 409
3. 缺少 `username` 且 `email` 格式錯誤 → 400，`errors` 陣列含兩筆錯誤
4. `age` 傳入 `"abc"` → 400
5. 查詢不存在的 `/api/users/9999` → 404

---

## 提示

- `pg` 套件的唯一鍵衝突 error code 為 `'23505'`，可用 `err.code === '23505'` 判斷。
- 統一錯誤 middleware 的簽名為四個參數：`(err, req, res, next)`，Express 依此識別它是錯誤 middleware。
- 驗證 middleware 可先將所有錯誤收集進陣列，最後再做 `if (errors.length) return next({ status: 400, errors })` 的傳遞。
- `process.env` 存放資料庫連線資訊，避免硬編碼在程式碼中。

## 進階挑戰（選做）

1. **使用 Joi 或 Zod 重寫驗證邏輯**，比較與手工驗證的差異，並說明哪種方式更易維護。
2. **加入 Request Logger Middleware**，每次請求都記錄 `[時間戳] METHOD /路徑 → 狀態碼` 到 console。
3. **實作 `PATCH /api/users/:id`**，僅更新傳入的欄位（partial update），並對傳入欄位套用相同驗證規則。
4. **撰寫整合測試**（使用 `supertest` + `jest`）：涵蓋成功新增、重複欄位衝突、驗證失敗三個情境。

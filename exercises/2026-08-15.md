# 第 6 週今日練習題：資料驗證與錯誤回應

## 題目說明

建立一個具備完整資料驗證機制的使用者管理 API。當客戶端傳入不合法的資料時，API 必須回傳清楚、一致的錯誤訊息，而非讓請求在資料庫層崩潰。本題的重點是「在進入資料庫之前就攔截錯誤」，並以標準化的 JSON 格式回傳錯誤資訊。

## 技術要求

- **Express.js**：路由設計、自訂驗證 middleware、全域錯誤處理 middleware
- **PostgreSQL**：使用者資料表（含 UNIQUE constraint），透過 pg 套件操作

## 具體任務

### 1. 建立資料表

在 PostgreSQL 建立 `users` 資料表：

```sql
CREATE TABLE users (
  id        SERIAL PRIMARY KEY,
  username  VARCHAR(30)  NOT NULL UNIQUE,
  email     VARCHAR(255) NOT NULL UNIQUE,
  age       INTEGER      CHECK (age >= 0 AND age <= 150),
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```

### 2. 實作驗證 middleware

建立 `middleware/validateUser.js`，對 `POST /users` 與 `PUT /users/:id` 的請求主體進行驗證：

| 欄位       | 規則                                              |
|------------|---------------------------------------------------|
| `username` | 必填、長度 3–30 字元、只能包含英數字與底線         |
| `email`    | 必填、須符合 email 格式                           |
| `age`      | 選填，若提供則必須為 0–150 之間的整數             |

驗證失敗時，middleware 必須回傳 `400 Bad Request`，格式如下：

```json
{
  "status": "error",
  "message": "Validation failed",
  "errors": [
    { "field": "username", "message": "Username must be 3–30 characters" },
    { "field": "email",    "message": "Invalid email format" }
  ]
}
```

一次回傳「所有」驗證錯誤，不要只回傳第一個。

### 3. 實作 CRUD 路由

| 方法   | 路徑           | 說明                    |
|--------|----------------|-------------------------|
| GET    | `/users`       | 取得所有使用者           |
| GET    | `/users/:id`   | 取得單一使用者           |
| POST   | `/users`       | 新增使用者（含驗證）     |
| PUT    | `/users/:id`   | 更新使用者（含驗證）     |
| DELETE | `/users/:id`   | 刪除使用者               |

### 4. 處理資料庫層錯誤

當 PostgreSQL 回傳違反 UNIQUE constraint 的錯誤（error code `23505`）時，攔截此錯誤並回傳：

```json
{
  "status": "error",
  "message": "Username or email already exists"
}
```
HTTP 狀態碼：`409 Conflict`

### 5. 實作全域錯誤處理 middleware

在 `app.js` 最底部掛載一個 4 個參數的錯誤處理 middleware `(err, req, res, next)`，負責：

- 將所有未預期的錯誤統一回傳 `500 Internal Server Error`
- 格式：`{ "status": "error", "message": "Internal server error" }`
- 在伺服器端 console 印出完整錯誤訊息（方便除錯）

### 6. 找不到資源的處理

- `GET /users/:id`、`PUT /users/:id`、`DELETE /users/:id`：若 id 不存在，回傳 `404 Not Found`
- 格式：`{ "status": "error", "message": "User not found" }`

## 提示

- Express 的錯誤處理 middleware 必須有 **4 個參數**（`err, req, res, next`），少一個就不會被視為錯誤處理器。
- 使用 `next(err)` 將錯誤往下傳給錯誤處理 middleware，不要在路由裡直接 `res.status(500).send()`。
- 可以自訂一個 `AppError` class 來區分「已預期的業務錯誤」與「未預期的系統錯誤」，讓錯誤處理 middleware 更容易判斷。
- 用 Postman 或 curl 測試各種壞資料（空欄位、不合法的 email、重複的 username）來驗證你的驗證邏輯。

## 進階挑戰（選做）

1. **引入 Joi 或 Zod**：將手刻的驗證邏輯改用 Joi 或 Zod schema 重新實作，比較兩種方式的可維護性。
2. **請求 logging middleware**：在每個請求進來時記錄 `[method] [path] [timestamp]`，在回應後記錄 `[status code] [response time ms]`。
3. **集中式錯誤碼**：建立一個 `errors/errorCodes.js` 檔案，定義所有業務錯誤碼（如 `USER_NOT_FOUND`、`DUPLICATE_EMAIL`），讓前端可以依錯誤碼進行程式化判斷，而不只是依賴 HTTP 狀態碼。

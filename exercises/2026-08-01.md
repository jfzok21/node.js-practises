# 第 4 週今日練習題：Express Middleware 實戰

## 題目說明

本週的核心主題是 **Express Middleware（中介軟體）**。Middleware 是 Express 架構中的靈魂，幾乎每一個請求都會經過它的處理。今天的練習將帶你從零開始建立自訂 Middleware，並整合 `body-parser`（或內建的 `express.json()`）與錯誤處理機制，打造一個具備完整請求管線的 Express 應用程式。

---

## 技術要求

- **Express.js**：使用 `app.use()` 掛載 Middleware，理解 `(req, res, next)` 的執行流程
- **body-parser / express.json()**：正確解析 `Content-Type: application/json` 的請求本體
- **自訂 Middleware**：實作請求紀錄器（Logger）與認證守衛（Auth Guard）
- **錯誤處理 Middleware**：實作四參數 `(err, req, res, next)` 的全域錯誤攔截器

---

## 具體任務

### 任務一：建立基礎 Middleware — 請求紀錄器（Request Logger）

1. 建立一個 `logger.js` Middleware，在每個請求進入時，於終端機輸出以下格式：
   ```
   [2026-08-01T10:00:00.000Z] GET /api/users - 200ms
   ```
   （時間戳、HTTP 方法、路徑、處理耗時）
2. 在 `app.js` 中用 `app.use()` 全域掛載這個 Logger。

---

### 任務二：整合 Body Parser

1. 使用 `express.json()` 讓 Express 能解析 JSON 請求本體。
2. 建立一個 `POST /api/echo` 路由，直接將收到的 `req.body` 以 JSON 格式回傳。
3. 驗證當 `Content-Type` 不是 `application/json` 時，`req.body` 的值為何？

---

### 任務三：自訂認證 Middleware — Token 守衛

1. 建立 `authGuard.js`：
   - 讀取請求標頭 `Authorization`（格式為 `Bearer <token>`）
   - 若 token 等於 `"secret-token-123"`，呼叫 `next()` 繼續
   - 若 token 不存在或錯誤，回傳 HTTP `401`：
     ```json
     { "error": "Unauthorized", "message": "Invalid or missing token" }
     ```
2. 建立以下受保護的路由（僅掛載 `authGuard`，不全域套用）：
   - `GET /api/protected` → 回傳 `{ "message": "歡迎！你已通過身份驗證" }`
   - `GET /api/public` → 不需驗證，直接回傳 `{ "message": "這是公開資源" }`

---

### 任務四：全域錯誤處理 Middleware

1. 在路由中建立一個 `GET /api/error-test` 路由，故意 `throw new Error("模擬伺服器錯誤")`。
2. 建立 `errorHandler.js`（四參數 Middleware）：
   - 攔截所有未處理的錯誤
   - 回傳 HTTP `500`：
     ```json
     {
       "error": "Internal Server Error",
       "message": "錯誤訊息內容",
       "timestamp": "ISO 格式時間"
     }
     ```
3. 確保 `errorHandler` 是 **最後一個** 被 `app.use()` 掛載的 Middleware。

---

### 任務五：Middleware 執行順序驗證

1. 建立一個路由 `GET /api/order-test`，在路由處理函式之前串接三個 inline Middleware：
   ```js
   app.get('/api/order-test',
     (req, res, next) => { console.log('Step 1'); next(); },
     (req, res, next) => { console.log('Step 2'); next(); },
     (req, res, next) => { console.log('Step 3'); next(); },
     (req, res) => res.json({ message: 'Done' })
   );
   ```
2. 呼叫此路由，觀察終端機輸出，理解 Middleware 的線性執行順序。

---

## 提示

- `next()` 不呼叫時，請求會**卡住**不繼續，務必在每個 Middleware 的適當位置呼叫它
- 錯誤處理 Middleware 必須有**四個參數** `(err, req, res, next)`，Express 才會識別為錯誤處理器
- 若要將錯誤傳遞給錯誤處理 Middleware，使用 `next(err)` 而非 `next()`
- `app.use()` 的掛載**順序**決定執行順序——Logger 應在最前面，errorHandler 應在最後面
- 使用 `Date.now()` 計算耗時：在請求進入時記錄開始時間，在 `res.on('finish', ...)` 事件中計算差值

---

## 進階挑戰（選做）

### 挑戰一：速率限制 Middleware（Rate Limiter）
實作一個簡單的記憶體型速率限制：
- 每個 IP 每分鐘最多允許 10 次請求
- 超過限制時回傳 HTTP `429 Too Many Requests`：
  ```json
  { "error": "Rate limit exceeded", "retryAfter": 60 }
  ```

### 挑戰二：請求 ID 注入
建立一個 Middleware，為每個請求生成唯一的 `X-Request-ID`（使用 `crypto.randomUUID()`），
並將其注入 `req.id` 與回應標頭，讓 Logger 也能記錄此 ID。

### 挑戰三：條件式 Middleware
使用 `unless` 模式，讓 `authGuard` 自動跳過特定路徑（例如 `/api/public`、`/health`），
不需要在每個公開路由手動排除。

# 第 6 週今日練習題：使用者資料驗證與完整錯誤回應

## 題目說明

建立一個使用者管理 API，針對所有輸入資料進行嚴格驗證，並回傳符合規範的錯誤訊息格式。你將學習如何在 Express + PostgreSQL 應用中實作健全的資料驗證層與統一的錯誤處理機制。

---

## 技術要求

- **Express.js**：自訂驗證 Middleware、全域錯誤處理 Middleware、統一錯誤回應格式
- **PostgreSQL**：users 資料表（含欄位約束）、UNIQUE 衝突偵測、資料庫層錯誤轉換

---

## 具體任務

### 1. 建立資料庫資料表

```sql
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  username VARCHAR(30) NOT NULL UNIQUE,
  email VARCHAR(255) NOT NULL UNIQUE,
  age INTEGER CHECK (age >= 0 AND age <= 150),
  role VARCHAR(20) NOT NULL DEFAULT 'user',
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```

### 2. 定義統一錯誤回應格式

所有錯誤回應必須遵循以下 JSON 結構：

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "輸入資料有誤",
    "details": [
      { "field": "email", "message": "email 格式不正確" },
      { "field": "age", "message": "age 必須介於 0 到 150 之間" }
    ]
  }
}
```

### 3. 實作輸入驗證 Middleware

建立 `middlewares/validateUser.js`，驗證規則如下：

| 欄位       | 規則                                              |
|------------|---------------------------------------------------|
| `username` | 必填、長度 3–30 字元、只允許英數字與底線           |
| `email`    | 必填、合法 email 格式                             |
| `age`      | 選填、若提供必須為整數且介於 0–150               |
| `role`     | 選填、只允許 `'user'` 或 `'admin'`               |

若驗證失敗，立即回傳 HTTP 422 與上述錯誤格式，**不得繼續執行**後續路由處理。

### 4. 建立 API 端點

| 方法   | 路徑              | 說明                         |
|--------|-------------------|------------------------------|
| POST   | `/api/users`      | 建立使用者（需驗證）          |
| GET    | `/api/users/:id`  | 取得單一使用者               |
| PUT    | `/api/users/:id`  | 更新使用者（需驗證）          |
| DELETE | `/api/users/:id`  | 刪除使用者                   |

### 5. 處理資料庫層錯誤

在資料庫操作時，捕捉並轉換以下 PostgreSQL 錯誤碼：

| PostgreSQL 錯誤碼 | HTTP 狀態碼 | 回傳 `code`        | 說明             |
|-------------------|-------------|---------------------|------------------|
| `23505`           | 409         | `CONFLICT`          | 唯一性約束衝突   |
| `23503`           | 422         | `FOREIGN_KEY_ERROR` | 外鍵約束違反     |
| `23514`           | 422         | `CHECK_CONSTRAINT`  | 欄位值超出範圍   |

### 6. 建立全域錯誤處理 Middleware

在 `app.js` 最後加入全域錯誤處理器（4 個參數：`err, req, res, next`），統一處理：
- 自訂驗證錯誤
- 資料庫錯誤
- 其他未預期錯誤（回傳 HTTP 500，**不得洩漏** stack trace 給客戶端）

---

## 提示

- 可使用 `validator` 套件（`npm install validator`）輔助 email 格式驗證，或自行撰寫正則表達式
- PostgreSQL 錯誤物件的錯誤碼存放於 `error.code` 屬性
- Express 的全域錯誤處理器必須宣告 **4 個參數**，否則不會被視為錯誤處理 Middleware
- 驗證 Middleware 收集**所有**錯誤後一次回傳，而非遇到第一個錯誤就停止
- 使用 `process.env.NODE_ENV` 判斷是否為開發環境，只在開發時回傳 stack trace

---

## 進階挑戰（選做）

1. **Schema 驗證整合**：改用 `joi` 或 `zod` 套件定義驗證 Schema，取代手寫驗證邏輯
2. **請求 ID 追蹤**：在每個請求加入 `X-Request-Id` 標頭（使用 `uuid`），並在錯誤回應中包含該 ID，方便日誌追蹤
3. **速率限制錯誤**：整合 `express-rate-limit`，當超過請求頻率時回傳 HTTP 429 與符合格式的錯誤訊息
4. **日誌記錄**：使用 `winston` 或 `pino` 記錄所有錯誤，區分 `warn`（用戶端錯誤 4xx）與 `error`（伺服器端錯誤 5xx）等級

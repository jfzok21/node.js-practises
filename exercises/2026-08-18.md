# 第 6 週今日練習題：使用者資料驗證與結構化錯誤回應

## 題目說明

建立一個使用者管理 API，對所有傳入資料進行嚴謹的驗證，並在資料不合法或發生錯誤時回傳一致且結構清晰的 JSON 錯誤訊息。本題的核心在於「防禦性輸入驗證」與「統一的錯誤格式」，這是生產環境 API 的基本要求。

---

## 技術要求

- **Express.js**：路由設計、自訂驗證 middleware、全域錯誤處理 middleware
- **PostgreSQL**：`users` 資料表（id、name、email、age、created_at），唯一鍵約束 (UNIQUE) on email

---

## 具體任務

### 1. 建立資料庫資料表

建立 `users` 資料表，欄位如下：

```sql
CREATE TABLE IF NOT EXISTS users (
  id         SERIAL PRIMARY KEY,
  name       VARCHAR(100) NOT NULL,
  email      VARCHAR(255) NOT NULL UNIQUE,
  age        INTEGER,
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```

### 2. 定義統一錯誤回應格式

所有錯誤回應都必須使用以下 JSON 結構：

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "輸入資料有誤",
    "details": [
      { "field": "email", "message": "email 格式不正確" }
    ]
  }
}
```

成功回應格式：

```json
{
  "success": true,
  "data": { ... }
}
```

### 3. 實作驗證 Middleware：`validateUser`

編寫一個可重用的 `validateUser` middleware，對 `req.body` 進行下列驗證：

| 欄位  | 規則 |
|-------|------|
| name  | 必填；長度 2–100 字元 |
| email | 必填；需符合 email 格式（含 `@` 與 `.`） |
| age   | 選填；若提供，必須是 18–120 之間的整數 |

驗證失敗時，回傳 HTTP **422**，並將所有違反規則的欄位一次列出（不要第一個錯就停止）。

### 4. 實作以下 API 端點

| 方法   | 路徑           | 說明 |
|--------|----------------|------|
| POST   | /users         | 建立使用者（套用 `validateUser`） |
| GET    | /users         | 取得所有使用者（按 created_at 降冪排序） |
| GET    | /users/:id     | 取得單一使用者（找不到回傳 404） |
| PUT    | /users/:id     | 更新使用者（套用 `validateUser`，找不到回傳 404） |
| DELETE | /users/:id     | 刪除使用者（找不到回傳 404） |

**特別處理**：POST `/users` 時，若 email 已存在，必須捕捉 PostgreSQL 的唯一鍵違反錯誤（錯誤碼 `23505`），回傳 HTTP **409** 與 `EMAIL_CONFLICT` 錯誤碼。

### 5. 全域錯誤處理 Middleware

在 `app.js` 最末加上全域錯誤處理器，捕捉所有未預期錯誤，統一回傳 HTTP **500**：

```js
// 四個參數代表這是錯誤處理 middleware
app.use((err, req, res, next) => {
  console.error(err.stack);
  res.status(500).json({
    success: false,
    error: {
      code: 'INTERNAL_ERROR',
      message: '伺服器發生錯誤，請稍後再試'
    }
  });
});
```

### 6. 手動測試

使用 `curl` 或 Postman 驗證以下情境：

- POST 送出空白 body → 422，列出所有缺失欄位
- POST 送出格式錯誤的 email → 422
- POST 送出 age = 15 → 422
- POST 成功建立使用者 → 201
- POST 重複 email → 409
- GET `/users/99999`（不存在） → 404

---

## 提示

- 驗證邏輯建議寫成純函式 `validate(body): errors[]`，再在 middleware 中呼叫，方便單元測試。
- 捕捉 PostgreSQL 唯一鍵錯誤：`if (err.code === '23505') { ... }`
- `parseInt()` 可能回傳 `NaN`，記得使用 `Number.isInteger()` 或 `isNaN()` 進行型別檢查。
- 路由中的 `try/catch` 記得呼叫 `next(err)` 將錯誤傳給全域 middleware。

## 進階挑戰（選做）

1. **使用第三方驗證套件**：以 `joi` 或 `zod` 重寫 `validateUser`，比較兩種寫法的差異。
2. **422 vs 400**：研究 HTTP 語意，說明為何驗證錯誤用 422 比 400 更準確。
3. **請求日誌 Middleware**：記錄每個請求的方法、路徑、狀態碼、回應時間（毫秒）。
4. **速率限制**：整合 `express-rate-limit`，限制同一 IP 每分鐘最多 30 次請求。

# 第 10 週今日 Node.js 練習題：輸入驗證與錯誤處理

## 題目說明

建立一個 Express API，實作完整的輸入驗證與錯誤處理機制。透過中介層（middleware）統一驗證請求資料，並以標準化的錯誤回應格式處理各種異常情況。

---

## 技術要求

- **概念**：輸入驗證、自定義錯誤類別、錯誤處理中介層、HTTP 狀態碼語義
- **需要的套件**：
  - `express`
  - `joi` 或 `zod`（擇一，用於 Schema 驗證）
  - `express-async-errors`（讓 async route handler 的錯誤自動傳遞至錯誤中介層）

---

## 具體任務

1. **建立自定義錯誤類別**  
   建立 `AppError` 類別，繼承自 `Error`，支援傳入 HTTP 狀態碼與錯誤訊息：
   ```
   new AppError(400, '使用者名稱不能為空')
   ```

2. **建立 Joi/Zod 驗證 Schema**  
   為「建立使用者」端點定義以下規則：
   - `username`：字串，必填，長度 3–20，僅允許英數字與底線
   - `email`：必填，合法 email 格式
   - `age`：數字，選填，介於 1–120

3. **建立驗證中介層**  
   撰寫 `validate(schema)` 函式，回傳一個 middleware，對 `req.body` 執行驗證；驗證失敗時拋出 `AppError(400, 錯誤訊息)`。

4. **建立路由**  
   - `POST /users`：套用驗證中介層，驗證通過後回傳 201 與 `{ message: '使用者建立成功', data: req.body }`
   - `GET /users/:id`：若 `id` 不是正整數，回傳 400 錯誤

5. **建立全域錯誤處理中介層**  
   置於所有路由之後，統一捕捉所有錯誤，並以以下格式回應：
   ```json
   {
     "status": "error",
     "statusCode": 400,
     "message": "具體的錯誤說明"
   }
   ```
   若為未預期錯誤（非 `AppError`），一律回傳 500，並在開發模式下印出 `err.stack`。

---

## 範例

```js
// POST /users  送出以下 body：
{
  "username": "hi",
  "email": "not-an-email"
}

// 預期回應（400）：
{
  "status": "error",
  "statusCode": 400,
  "message": "\"username\" length must be at least 3 characters long"
}

// POST /users  送出合法 body：
{
  "username": "alice_01",
  "email": "alice@example.com",
  "age": 25
}

// 預期回應（201）：
{
  "message": "使用者建立成功",
  "data": { "username": "alice_01", "email": "alice@example.com", "age": 25 }
}
```

---

## 提示

- Joi 的基本用法：`Joi.object({ field: Joi.string().min(3).required() })`
- `schema.validate(data, { abortEarly: false })` 可取得所有錯誤，而非只有第一個
- Express 錯誤中介層需要四個參數：`(err, req, res, next)`，少一個就不會被識別為錯誤中介層
- 使用 `express-async-errors` 後，無需在每個 async handler 中手動 `try/catch` 再呼叫 `next(err)`

---

## 學習重點（跟後端 API 的關聯）

- **防禦性程式設計**：永遠不信任外部輸入。在資料進入業務邏輯之前先行驗證，可避免髒資料存入資料庫或引發不預期的執行期錯誤。
- **統一錯誤格式**：前端開發者（或 API 消費者）只需處理一種錯誤結構，大幅降低溝通成本。
- **HTTP 狀態碼語義**：400 Bad Request（客戶端問題）vs 500 Internal Server Error（伺服器問題）的正確使用，是 REST API 設計的基本功。
- **錯誤中介層集中管理**：將 `try/catch` 邏輯從每個路由中抽離，讓路由只專注於業務邏輯，提升可讀性與可維護性。

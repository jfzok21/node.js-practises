# 第 6 週今日 Node.js 練習題：自訂速率限制 Middleware（Rate Limiter）

## 題目說明

Rate limiting（速率限制）是保護 API 不被濫用的必備機制。本題要求你不使用任何第三方套件，純手工實作一個基於 IP 的速率限制 middleware，並整合進 Express 應用程式中。

## 技術要求

- 概念：Express middleware、`Map` 資料結構、時間窗口演算法（Fixed Window）、HTTP 429 狀態碼
- 需要的套件：`express`（`npm install express`）

## 具體任務

1. **建立 `rateLimiter.js`**，實作並匯出一個 `createRateLimiter(options)` 工廠函式：
   - 接受選項物件 `{ windowMs, max, message }`
     - `windowMs`：時間窗口長度（毫秒），例如 `60000`（1 分鐘）
     - `max`：窗口內允許的最大請求次數，例如 `5`
     - `message`：超限時回傳的錯誤訊息
   - 使用 `Map` 在記憶體中記錄每個 IP 的請求次數與窗口開始時間
   - 回傳一個 Express middleware 函式 `(req, res, next) => {}`

2. **實作速率限制邏輯**：
   - 以 `req.ip` 作為識別鍵
   - 若該 IP 的時間窗口已過期，重設計數器與時間戳
   - 若請求次數未超過 `max`，呼叫 `next()` 並在 response header 加上：
     - `X-RateLimit-Limit`：最大次數
     - `X-RateLimit-Remaining`：剩餘次數
     - `X-RateLimit-Reset`：窗口重設的 Unix timestamp（秒）
   - 若超過限制，回傳 HTTP 429 與 JSON `{ "error": message, "retryAfter": <剩餘秒數> }`

3. **建立 `app.js`**，監聽 port 3000，並設定兩條路由，各自套用不同寬鬆程度的 rate limiter：
   - `GET /api/public`：每分鐘最多 **10** 次，超限訊息 `"公開 API 請求過於頻繁"`
   - `GET /api/strict`：每分鐘最多 **3** 次，超限訊息 `"嚴格端點：請稍後再試"`

4. **建立全域錯誤處理 middleware**（放在所有路由之後）。

## 範例

```js
// rateLimiter.js 用法範例
const createRateLimiter = require('./rateLimiter');

const limiter = createRateLimiter({
  windowMs: 60000, // 1 分鐘
  max: 5,
  message: '請求次數超過限制，請稍後再試'
});

app.use('/api/protected', limiter, protectedRouter);

// --- 測試情境 ---

// 第 1 次請求（成功）
// curl http://localhost:3000/api/strict
// Headers: X-RateLimit-Limit: 3, X-RateLimit-Remaining: 2
// Body: { "message": "嚴格資料" }

// 第 4 次請求（超限）
// curl http://localhost:3000/api/strict
// HTTP 429
// Body: { "error": "嚴格端點：請稍後再試", "retryAfter": 47 }
```

## 提示

- `req.ip` 在本機測試時通常為 `"::1"`（IPv6 localhost），這是正常的。
- `Date.now()` 回傳毫秒，除以 1000 可轉為秒（Unix timestamp）。
- 將計數器存在 `Map` 中：`{ count: number, windowStart: number }`。
- 記得在超限時加上 `Retry-After` header（秒數），這是 HTTP 規範的一部分。
- 每次請求都要先判斷窗口是否過期，**再**判斷是否超限。

## 學習重點（跟後端 API 的關聯）

Rate limiting 是生產環境 API 的標準配備，常見應用如下：

| 場景 | 設定建議 |
|---|---|
| 公開 REST API | 每分鐘 60 次 / IP |
| 登入端點 | 每 15 分鐘 5 次（防暴力破解）|
| 付費 API 方案 | 依用戶等級設定不同上限 |
| Webhook 接收 | 每秒 10 次（避免佇列爆炸）|

實際專案通常使用 Redis 取代 `Map`，以支援多伺服器節點共享計數，第 8 週的 PostgreSQL 單元會帶你接觸類似的持久化概念。

## 進階挑戰（選做）

1. 實作 **Sliding Window** 演算法（滑動時間窗口），取代固定窗口，讓限制更平滑，避免窗口邊界的突發流量問題。
2. 加入 **IP 白名單**功能：在選項中接受 `whitelist: string[]`，白名單內的 IP 跳過速率限制直接通過。
3. 新增 `GET /api/status` 路由，回傳當前所有 IP 的速率限制狀態（計數、窗口剩餘秒數），方便監控。

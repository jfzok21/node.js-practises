# 第 10 週今日 Node.js 練習題：會員註冊 API 的輸入驗證與錯誤處理

## 題目說明

建立一個 Express API，實作使用者「會員註冊」端點。這個端點要能夠嚴格驗證輸入資料，並透過統一的錯誤處理機制，回傳清楚且一致的錯誤訊息。這是後端 API 開發中最重要的防禦層之一。

---

## 技術要求

- **概念：** 輸入驗證（Input Validation）、自定義錯誤類別（Custom Error Class）、Express 錯誤處理 Middleware、HTTP 狀態碼
- **需要的套件：**
  - `express`
  - `joi`（輸入驗證）
  - `bcrypt`（密碼雜湊，選做）

安裝指令：
```bash
npm install express joi bcrypt
```

---

## 具體任務

1. **建立自定義錯誤類別 `AppError`**
   - 繼承 `Error`
   - 包含 `statusCode` 屬性（例如 400、404、409）
   - 包含 `isOperational` 旗標，區分「已知的業務錯誤」與「系統意外錯誤」

2. **建立 Joi 驗證 Schema**
   - `username`：必填，字串，長度 3–20，只允許英數字與底線
   - `email`：必填，合法的 email 格式
   - `password`：必填，最少 8 字元，需包含至少一個數字與一個大寫字母
   - `age`：選填，數字，18–120 之間

3. **建立 `POST /api/register` 端點**
   - 使用 Joi Schema 驗證 `req.body`
   - 驗證失敗時，拋出包含所有錯誤欄位的 `AppError`（狀態碼 400）
   - 模擬「Email 已存在」的情境（用一個假的已存在 Email 清單），重複時回傳 409

4. **建立全域 Express 錯誤處理 Middleware**
   - 捕捉所有拋出的 `AppError`
   - 回傳統一的 JSON 格式：
     ```json
     {
       "status": "error",
       "statusCode": 400,
       "message": "驗證失敗",
       "errors": ["password 必須包含至少一個大寫字母"]
     }
     ```
   - 對於非 `isOperational` 的錯誤（系統錯誤），回傳 500 並只顯示通用訊息

5. **測試以下情境**
   - 成功註冊 → 201
   - 欄位缺失 → 400
   - Email 格式錯誤 → 400
   - 密碼強度不足 → 400
   - Email 重複 → 409

---

## 範例

```js
// 請求 (POST /api/register)
{
  "username": "john_doe",
  "email": "john@example.com",
  "password": "Secret123",
  "age": 25
}

// 成功回應 (201 Created)
{
  "status": "success",
  "message": "註冊成功",
  "data": {
    "username": "john_doe",
    "email": "john@example.com"
  }
}

// 驗證失敗回應 (400 Bad Request)
{
  "status": "error",
  "statusCode": 400,
  "message": "驗證失敗",
  "errors": [
    "password 長度至少需要 8 個字元",
    "password 必須包含至少一個大寫字母"
  ]
}

// Email 重複回應 (409 Conflict)
{
  "status": "error",
  "statusCode": 409,
  "message": "此 Email 已被註冊",
  "errors": []
}
```

## 提示

- Joi 的 `schema.validate(data, { abortEarly: false })` 可以一次回傳**所有**錯誤，而非只回傳第一個錯誤
- Express 的錯誤處理 Middleware 必須有 **4 個參數**：`(err, req, res, next)`
- 使用 `next(err)` 將錯誤傳遞給錯誤 Middleware，不要直接在 route 裡 `res.send()`
- 可以用 `password: Joi.string().min(8).pattern(/^(?=.*[A-Z])(?=.*\d)/)` 做複合密碼驗證

## 學習重點（跟後端 API 的關聯）

輸入驗證是 API 的「第一道防線」：

| 概念 | 用途 |
|------|------|
| Joi Schema | 定義並驗證請求資料的格式與規則 |
| 自定義 AppError | 統一錯誤結構，讓前端知道如何處理 |
| 錯誤處理 Middleware | 集中處理所有錯誤，避免重複的 try/catch |
| 適當的 HTTP 狀態碼 | 讓 API 語義清楚（400/404/409/500） |

實際的專案中，這個模式幾乎出現在每一個接收使用者輸入的端點。

## 進階挑戰（選做）

1. **整合 bcrypt**：在成功驗證後，使用 `bcrypt.hash(password, 10)` 將密碼雜湊後儲存（用 `Map` 模擬 DB）
2. **自定義 Joi 錯誤訊息**：用繁體中文回傳錯誤訊息，例如 `password: '密碼長度至少 8 個字元'`
3. **Rate Limiting**：加入 `express-rate-limit` 套件，限制同一 IP 每分鐘最多嘗試 5 次
4. **非同步錯誤捕捉**：建立 `asyncWrapper(fn)` 高階函式，自動把 async route handler 的錯誤傳給 `next`

```js
// asyncWrapper 範例
const asyncWrapper = (fn) => (req, res, next) => {
  Promise.resolve(fn(req, res, next)).catch(next);
};
```

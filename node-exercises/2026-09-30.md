# 第 13 週今日 Node.js 練習題：短網址服務 API 實戰專案

## 題目說明

今天的實戰專案是建立一個完整的「短網址服務 API」（URL Shortener Service）。這個服務讓使用者可以將長網址縮短成易於分享的短碼，並追蹤每個短網址的點擊次數與使用者資訊。專案整合了 JWT 身份驗證、輸入驗證、中介軟體設計、錯誤處理，以及 Jest 測試，是一個貼近真實產品的後端練習。

---

## 技術要求

- **概念**：Express、短碼生成演算法、JWT 身份驗證、REST API 設計、輸入驗證、統一錯誤處理、Jest 整合測試
- **需要的套件**：
  ```
  express
  jsonwebtoken
  bcryptjs
  express-validator
  nanoid
  dotenv
  jest
  supertest
  ```
- **資料儲存**：使用記憶體內物件模擬資料庫（不需要實際 DB）

## 具體任務

### 1. 專案初始化
建立 `url-shortener/` 目錄，執行 `npm init -y`，安裝上述套件，並建立 `.env` 檔：
```
PORT=3000
JWT_SECRET=urlsecretkey456
BASE_URL=http://localhost:3000
```

### 2. 使用者功能（`/api/auth`）
- `POST /api/auth/register`：接收 `name`、`email`、`password`，密碼使用 `bcryptjs` 雜湊後存入記憶體，回傳使用者資訊（不含密碼）
- `POST /api/auth/login`：驗證 email 與密碼，成功後回傳 JWT token（有效期 2 小時）

### 3. JWT 驗證中介軟體
建立 `middleware/auth.js`，從 `Authorization: Bearer <token>` 標頭中解析並驗證 JWT。  
- 驗證失敗（無 token、token 過期、格式錯誤）一律回傳 `401 Unauthorized`

### 4. 短網址 CRUD（`/api/urls`，需登入）

所有路由都須通過 JWT 驗證，且使用者只能管理自己建立的短網址：

- `POST /api/urls`：建立短網址
  - 接收 `originalUrl`（必填）與 `customCode`（選填，自訂短碼）
  - 若未提供 `customCode`，使用 `nanoid(6)` 自動生成 6 碼短碼
  - 若 `customCode` 已被佔用，回傳 `409 Conflict`
  - 回傳完整短網址：`{ shortUrl: "http://localhost:3000/r/abc123", ... }`

- `GET /api/urls`：取得目前使用者的所有短網址列表（含點擊次數）

- `GET /api/urls/:code`：取得單一短網址的詳細資訊（含點擊記錄）

- `DELETE /api/urls/:code`：刪除短網址（只能刪除自己的）

### 5. 重導向端點（公開，不需登入）
- `GET /r/:code`：根據短碼找到原始網址，記錄一筆點擊（儲存 `timestamp` 與 `userAgent`），然後回傳 `302 Found` 並重導向至原始網址
  - 若短碼不存在，回傳 `404 Not Found`

### 6. 輸入驗證
使用 `express-validator` 驗證：
- `register`：`email` 必須為有效格式，`password` 至少 8 個字元，`name` 不得為空
- `createUrl`：`originalUrl` 必須為有效 URL（以 `http://` 或 `https://` 開頭），`customCode` 若有提供則只能包含英數字與連字號（`/^[a-zA-Z0-9-]+$/`），且長度 3–20 字元

### 7. 統一錯誤處理中介軟體
建立 `middleware/errorHandler.js`，回傳標準格式：
```json
{ "error": "訊息說明", "details": [] }
```

### 8. 撰寫 Jest 整合測試
使用 `supertest` 測試至少以下情境：
- 成功註冊與登入流程
- 未登入呼叫 `POST /api/urls` 應回傳 `401`
- 帶有效 token 成功建立短網址，回應包含 `shortUrl`
- 嘗試建立已使用的 `customCode` 應回傳 `409`
- `GET /r/:code` 正確重導向並累積點擊次數
- 刪除不屬於自己的短網址應回傳 `403`

## 提示

- `nanoid` 在 ESM 環境下的 import 語法不同；若使用 CommonJS（`require`），安裝 `nanoid@3`（`npm install nanoid@3`），可直接 `const { nanoid } = require('nanoid')`
- 以短碼為 key 將 url 資料存入物件（`const urls = {}`），查找效率為 O(1)
- 重導向端點要在 JWT 中介軟體**外**，因為訪客也能點擊短網址
- 測試重導向時，`supertest` 預設會跟隨 302 重導向；使用 `.redirects(0)` 關閉自動跟隨，才能驗證 302 狀態碼與 `Location` 標頭

## 學習重點（跟後端 API 的關聯）

這個練習涵蓋真實短網址服務的核心後端設計：

- **公開 vs. 受保護路由**：重導向端點公開，管理端點需驗證，這是 API 設計中常見的「混合存取控制」模式
- **唯一性約束**：短碼不可重複，類似資料庫的 `UNIQUE` 約束，需在應用層處理衝突（`409`）
- **分析/追蹤**：記錄點擊事件是常見的業務需求，展示了如何在 API 回應以外的副作用中寫入資料
- **短碼生成**：`nanoid` 是業界常用的隨機 ID 生成方案，了解其使用有助於建立各類需要唯一識別碼的系統

## 進階挑戰（選做）

1. **過期時間**：在建立短網址時允許設定 `expiresAt` 欄位，過期後重導向應回傳 `410 Gone`
2. **點擊統計**：在 `GET /api/urls/:code` 的回應中加入按日期分組的統計（例如過去 7 天每日點擊數）
3. **QR Code**：在 `POST /api/urls` 的回應中加入 QR Code 圖片（使用 `qrcode` 套件生成 base64 字串）
4. **Rate Limiting**：使用 `express-rate-limit` 限制 `POST /api/urls` 每位使用者每分鐘最多建立 10 個短網址

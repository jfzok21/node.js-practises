# 第 7 週今日 Node.js 練習題：待辦任務管理 REST API（篩選、分頁與部分更新）

## 題目說明

在前兩天的書籍管理 API 基礎上，今天進階到更貼近生產環境的設計：**查詢篩選**、**分頁**，以及使用 `PATCH` 做**部分更新**。這三項功能在幾乎所有後端 API 專案中都不可或缺，是面試與工作中最常被考核的 REST API 技能。

你將打造一個「待辦任務（Todo）」管理 API，並讓前端可以靈活地依狀態、優先度篩選任務，以及分頁瀏覽大量資料。

---

## 技術要求

- **概念**：REST 動詞（GET / POST / PATCH / DELETE）、Query String 篩選、分頁（page / limit）、HTTP 狀態碼
- **需要的套件**：`express`（`npm install express`）

---

## 具體任務

### 1. 資料結構

在記憶體中維護一個 `tasks` 陣列，每筆任務格式如下：

```js
{
  id: 1,
  title: "學習 REST API",
  status: "pending",      // "pending" | "in_progress" | "done"
  priority: "high",       // "low" | "medium" | "high"
  createdAt: "2026-08-22T08:00:00.000Z"
}
```

預先放入至少 **10 筆**測試資料，涵蓋不同 status 與 priority 組合。

---

### 2. 建立以下 REST 路由

| 方法   | 路由                 | 說明                                 |
|--------|----------------------|--------------------------------------|
| GET    | `/tasks`             | 列出所有任務（支援篩選 + 分頁）       |
| GET    | `/tasks/:id`         | 取得單一任務                         |
| POST   | `/tasks`             | 新增任務                             |
| PATCH  | `/tasks/:id`         | 部分更新（只更新提供的欄位）          |
| DELETE | `/tasks/:id`         | 刪除任務                             |

---

### 3. `GET /tasks` 支援的 Query Parameters

| 參數       | 說明                            | 範例                  |
|------------|---------------------------------|-----------------------|
| `status`   | 依狀態篩選                      | `?status=pending`     |
| `priority` | 依優先度篩選                    | `?priority=high`      |
| `page`     | 第幾頁（預設 1）                | `?page=2`             |
| `limit`    | 每頁幾筆（預設 5）              | `?limit=3`            |

所有參數可以**組合使用**：`GET /tasks?status=pending&priority=high&page=1&limit=3`

---

### 4. 統一回應格式

**成功（列表）**：
```json
{
  "success": true,
  "data": [...],
  "pagination": {
    "total": 8,
    "page": 1,
    "limit": 5,
    "totalPages": 2
  }
}
```

**成功（單筆）**：
```json
{
  "success": true,
  "data": { "id": 1, "title": "...", "status": "pending", "priority": "high" }
}
```

**失敗**：
```json
{
  "success": false,
  "error": "Task not found"
}
```

---

### 5. PATCH 部分更新邏輯

`PATCH /tasks/:id` 只更新 request body 中存在的欄位，不覆蓋其他欄位：

```js
// 只更新 status，其他欄位保持不變
// PATCH /tasks/1
// Body: { "status": "done" }
```

## 範例

```js
// GET /tasks?status=pending&priority=high&page=1&limit=2
// 回應：
{
  "success": true,
  "data": [
    { "id": 1, "title": "學習 REST API", "status": "pending", "priority": "high", "createdAt": "..." },
    { "id": 3, "title": "撰寫單元測試", "status": "pending", "priority": "high", "createdAt": "..." }
  ],
  "pagination": {
    "total": 4,
    "page": 1,
    "limit": 2,
    "totalPages": 2
  }
}

// PATCH /tasks/1
// Body: { "status": "in_progress" }
// 回應：
{
  "success": true,
  "data": { "id": 1, "title": "學習 REST API", "status": "in_progress", "priority": "high", "createdAt": "..." }
}
```

## 提示

- **篩選**：先 `.filter()` 資料，再做分頁計算
- **分頁**：用 `.slice((page-1)*limit, page*limit)` 取出該頁資料
- **PATCH vs PUT**：`PUT` 替換整筆資料；`PATCH` 只更新提供的欄位（用 `Object.assign` 或展開運算子 `{ ...task, ...updates }`）
- 驗證 `status` 與 `priority` 的值是否合法，不合法回傳 `400 Bad Request`
- 找不到任務時回傳 `404 Not Found`

---

## 學習重點（跟後端 API 的關聯）

| 今日概念         | 真實後端場景                                          |
|------------------|-------------------------------------------------------|
| Query 篩選       | 電商商品搜尋、CRM 客戶篩選、後台報表                  |
| 分頁             | 幾乎所有列表 API 都需要，避免一次回傳百萬筆資料        |
| PATCH 部分更新   | 只改訂單狀態、只更新用戶頭像，不需要傳整個物件         |
| 統一錯誤格式     | 前端可以用同一套邏輯處理所有 API 錯誤                  |

## 進階挑戰（選做）

1. **排序**：支援 `?sort=priority&order=desc`（高優先度排前面）
2. **關鍵字搜尋**：支援 `?q=測試`，在 `title` 中模糊搜尋
3. **批次更新**：`PATCH /tasks/bulk`，body 傳 `{ "ids": [1,2,3], "status": "done" }`，一次更新多筆
4. **Express Router**：將任務路由拆分到 `routes/tasks.js`，主程式只 `app.use('/tasks', tasksRouter)`
